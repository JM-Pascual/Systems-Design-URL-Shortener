# Questions

- Can we directly encode with b62 a URL as it comes?
- What's the issue in part 1 with in-memory storage and potential clustering / multiple instance spawning? If we scale our service into multiple instances, each one will have a different storage access layer.
- Why should we use 307 or 302 instead of 301?
- `code TEXT PRIMARY KEY` versus a separate `id SERIAL PRIMARY KEY` with a `UNIQUE` index on `code` — what does the second buy you, and is it worth the extra index?
- Postgres's `nextval()` is non-transactional, so a rolled-back transaction never reclaims the sequence value it consumed. Why is that the right trade-off for concurrency, and why doesn't the resulting gap in codes threaten correctness?
- In Tier 4.3, a rebuild that finds no row frees the key with `DELEX code IFEQ note` instead of a plain `DEL code`. Trace what a plain `DEL` would do if the note had already expired and another reader had left its own note, or if a write had already cancelled the note and a new rebuild had cached a fresh URL. Why does a compare-and-delete need to be one command, rather than a `GET` followed by a `DEL`?
- Is simply relying on sliding TTL (reset a key's expiry on every hit) plus `allkeys-lfu` eviction a bad caching policy in the general case? Think it through before answering: sliding TTL never lets a key expire on its own as long as *something* keeps reading it, however rarely — so isn't that a problem? (Not really — trace what happens the moment memory pressure actually forces a choice: LFU is still the one deciding who goes, and it's still correctly picking the least-accessed key among everything sliding TTL kept alive. Sliding TTL only changes who's in the candidate pool; it doesn't touch who wins when eviction has to happen.)
- Rebuilding a lost Bloom filter means a full scan of `links`, because Postgres is the only place that still has every code. An alternative is to save the filter periodically with `BF.SCANDUMP`, restore the latest copy with `BF.LOADCHUNK`, and then add only the codes created after that copy. How does this parallel Raft's snapshots, where a node restores a snapshot and replays only the log entries after it? Then push on where the analogy breaks: Raft's log has a strict total order and a last-included index, while `created_at` isn't commit order, since transactions can commit out of order. So how much overlap does the catch-up need, and which property of adding to a Bloom filter makes that overlap safe? And what can't the catch-up replay, given that a Bloom filter has no removal operation and `DELETE` leaves no row to read?
